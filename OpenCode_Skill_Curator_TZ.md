# Техническое задание: OpenCode Skill Curator

**Версия:** 1.0  
**Дата:** 13 ноября 2026 г.  
**Статус:** спецификация к реализации  
**Целевая платформа:** OpenCode v2 (`@opencode/plugin`)  
**Интеграция:** V.A.L.E.R.I.A. (опциональная, через RPC API)  
**Формат поставки:** самостоятельный npm-плагин OpenCode с серверной частью, TUI, публичным RPC-контрактом, документацией и тестами.

## 1. Назначение

Разработать плагин **OpenCode Skill Curator**, который автоматически извлекает переносимые знания из уже выполненных задач и диалогов OpenCode, создаёт и обновляет навыки (skills), проводит ревизию библиотеки, объединяет похожие навыки, выявляет неактуальные, архивирует их и поддерживает возможность просмотра и управления всей библиотекой вручную.

**Ключевое требование:** VALERIA должна получать полный программный контроль над функциями плагина — чтение каталога и истории, управление навыками, запуск менеджера и ревизий, создание/одобрение изменений, изменение настроек, запуск/приостановка/отмена фоновых заданий, статистика и события. При этом плагин **обязан полноценно работать без VALERIA**.

**Критическое уточнение:** внутренние LLM-задачи **не обязаны** проходить через очередь VALERIA. Режим исполнения задаётся пользователем глобально, для каждого типа задачи и для конкретного запуска.

## 2. Термины

- **Skill** — пакет навыка, содержащий `SKILL.md` и, возможно, `scripts/`, `references/`, `templates/`, `assets/` и другие зависимые файлы.
- **Learner** — подсистема поиска переносимых знаний в завершённых сессиях/задачах.
- **Curator** — подсистема ревизии, консолидации, актуализации и архивирования скилов.
- **Manager** — единая управляющая подсистема с TUI и RPC API; это не обязательная отдельная LLM-сессия.
- **Proposal** — неизменяемое предложение на изменение одного или нескольких скилов с diff, обоснованием, источниками и оценкой риска.
- **Job** — фоновое задание: анализ истории, ревизия библиотеки, генерация предложения, проверка или публикация.
- **Executor** — механизм исполнения LLM-части задания.
- **Workspace** — область проекта OpenCode; для VALERIA должна иметь привязку к владельцу/арендатору (tenant).
- **Managed skill** — скил, который разрешено автоматически обслуживать по явно заданной политике.
- **Adopt** — явная передача вручную созданного скила под автоматическое обслуживание.

## 3. Объём и границы

### 3.1. Обязательно

1. Обнаружение всех доступных OpenCode скилов и управляемого каталога: глобальных, проектных и доступных внешних источников.
2. Просмотр полного содержимого навыка и связанного пакета, метаданных, истории версий и статистики использования.
3. Ручные операции: создание, редактирование, переименование, дублирование, объединение, архивирование, восстановление, закрепление (`pin`), блокировка модификаций (`lock`), передача под управление (`adopt`), экспорт, просмотр diff, откат версии.
4. Автоматическое накопление опыта после завершённых сессий; пакетный и ретроспективный анализ истории.
5. LLM-анализ качества скилов: новые навыки, патчи, дубликаты, объединение, разделение перегруженных скилов, устаревшие инструкции.
6. Периодическая детерминированная ревизия без LLM и опциональная глубокая LLM-ревизия.
7. Версионирование, архив без потери данных, безопасное восстановление, журнал изменений.
8. TUI-менеджер, вызываемый командой `/skills-manager`, и дополнительные команды для быстрого запуска операций.
9. Типизированный RPC-контракт, доступный из VALERIA и других внешних клиентов через сервер OpenCode.
10. Настраиваемый механизм исполнения LLM-задач, независимый от обязательного наличия VALERIA.
11. Изоляция workspace/tenant и полномочий внешнего клиента.
12. Безопасная обработка транскриптов: секреты, приватные данные, prompt injection, недоверенные tool outputs.

### 3.2. Не требуется в первой версии

- Обучение или fine-tuning весов модели.
- Автоматическое опубликование скилов в публичных репозиториях/маркетплейсах.
- Автоматическое скачивание и исполнение произвольных скриптов из найденных скилов.
- Обязательная внешняя векторная БД; допускается локальный индекс и эвристический поиск.
- Изменение исходного кода OpenCode или VALERIA для базовой автономной работы плагина.

## 4. Архитектура

```text
OpenCode v2
  ├─ Server Plugin
  │    ├─ Skill Catalog / Package Store
  │    ├─ History Collector + Importer
  │    ├─ Learner + Curator
  │    ├─ Proposal Engine + Validator
  │    ├─ Job Scheduler + Executor Router
  │    ├─ Audit / Usage / Version Store
  │    └─ RPC Server (skill-curator.v1)
  ├─ TUI Plugin
  │    └─ /skills-manager: список / поиск / diff / настройки / jobs
  └─ Optional GUI Plugin (не блокирует выпуск)

RPC API  <─────────────────────► VALERIA / другие клиенты
                                  ├─ панель менеджера скилов
                                  ├─ администрирование
                                  └─ необязательный исполнитель заданий
```

Управляющая бизнес-логика располагается **только в серверном ядре**; TUI, VALERIA и другие клиенты обращаются к одинаковым методам. Не допускаются отдельные несовместимые правила доступа или обработки файлов в разных интерфейсах.

Пакет экспортирует `./server` (или основной экспорт), `./tui`, `./rpc`; `./gui-experimental` — необязателен. Примерный стек: TypeScript, `@opencode/plugin`, `@opencode/client`, JSON Schema/Zod, SQLite или иная транзакционная локальная БД. Точный выбор библиотеки БД оставляется реализации при сохранении API и гарантий целостности.

## 5. Модель хранения

### 5.1. Источники навыков и области видимости

Вести каталог доступных навыков с полями:

- `skill_id`: стабильный идентификатор внутри каталога, отличный от изменяемого названия;
- `name`, `description`, `scope`: `global | workspace | external`;
- `tenant_id`, `workspace_id` (если применимо), `source`, `source_path`;
- `owner`: `plugin | user | third_party | unknown`;
- `management_policy`: `managed | manual | readonly`;
- `state`: `active | stale | archived | superseded`;
- `pinned`, `locked`, `created_at`, `updated_at`, `last_used_at`;
- `use_count`, `view_count`, `patch_count` (все значения с источником наблюдения и временем обновления);
- `revision`, `content_hash`, `package_hash`, `replaced_by`, `source_session_ids`;
- `validation_status`, `risk_level`, `version_history`.

`owner` и `management_policy` — разные сущности: неизвестное авторство нельзя автоматически считать согласием на обслуживание.

Обнаруживать все доступные OpenCode навыки через поддерживаемый Skills API (`ctx.skill.list()`), при необходимости дополнительно индексировать только настроенные разрешённые директории. Записи внешних/сторонних источников по умолчанию `readonly`; доступность в каталоге не подразумевает права записи на диск.

Создаваемые плагином скилы записывать в выбранную пользователем глобальную/проектную директорию в форме пакета с `SKILL.md`. Обновление видимости выполняется через `ctx.skill.reload()` либо совместимый механизм выбранной версии SDK.

### 5.2. Данные плагина

Хранить раздельно:

- `skills`: метаданные каталога;
- `skill_versions`: снимки пакета/manifest и ссылки на сохранённые файлы;
- `sessions`: курсоры обработки и provenance;
- `learning_candidates`: извлечённые повторно используемые наблюдения;
- `proposals`, `proposal_changes`: предложения, diff и решения;
- `jobs`, `job_attempts`, `job_leases`: задания и исполнение;
- `events`, `audit_log`: события и журнал действий;
- `settings`: глобальные и scoped настройки;
- `usage`: факты использования (без предположения, что отсутствие фактов означает отсутствие использования).

Всю долговременную информацию хранить вне жизненного цикла одной сессии; после перезапуска состояние и незавершённые задания восстанавливаются. Секреты не сохранять в plaintext.

## 6. Skill Learner: получение знаний из истории

### 6.1. Входные данные

История обычных диалогов, завершённых задач, дочерних сессий и их результатов, включая при доступности:

- пользовательскую цель и контекст проекта;
- шаги агента, инструментальные вызовы и результаты;
- ошибки, повторные попытки, подтверждённые исправления;
- финальный результат, явный пользовательский feedback;
- применённые скилы и их эффект;
- ссылки на записи-источники для трассировки.

Анализировать не только полные сессии, но и законченные этапы долгих задач. Извлечение может запускаться после завершения задачи и пакетно по истории. Не считать непроверенную догадку агента успешным решением.

### 6.2. Сбор и восстановление

1. Подписаться на документированный поток событий OpenCode (`ctx.event.subscribe`) и соответствующие доступные lifecycle/tool hooks.
2. При завершении работы/этапа ставить событие в durable backlog, не вызывая тяжёлую LLM непосредственно в обработчике события.
3. Использовать `ctx.session.list()` и `ctx.session.context()` для чтения доступного контекста; не считать этот метод гарантией полного сырого архива всех tool outputs. Если требуемых частей нет, брать их из собственного сборщика событий или через предусмотренный импортёр истории.
4. Поддержать явный импорт сессий/транскриптов от VALERIA через API с проверкой владельца и происхождения.
5. Дедупликация по `(source_instance, session_id, stage_id, content_hash)`; хранение курсора; повторная обработка по запросу без дублирования результатов.
6. Исключить внутренние сессии самого плагина посредством metadata/системного реестра; не обучаться на Curator/Learner, чтобы избежать рекурсии.

### 6.3. Отбор знаний

Промежуточная сущность `LearningCandidate` содержит: `title`, `problem`, `solution`, `conditions`, `evidence`, `failures`, `confidence`, `scope`, `reusability_score`, `source_refs`, `sensitive_flags`.

Кандидаты ранжируются по переносимости, повторяемости, подтверждённости, специфичности проекта и потенциальной экономии. Не создавать новый скил из каждого диалога. Если знание уже покрывается навыком, предлагать `patch`; если дублирует существующее — `merge`/`skip`.

### 6.4. Триггеры

Конфигурируемые триггеры: `on_session_end`, `on_stage_end`, `every_n_sessions`, `interval`, `manual_only`, `on_demand` (RPC/TUI). Поддержать `min_age`, `debounce`, `quiet_hours`, `max_backlog`, `retention_days`, бюджет токенов/денег, минимальное качество источника. Первый запуск не должен внезапно обрабатывать всю архивную историю без явной настройки ретроспективного импорта.

## 7. Skill Curator: обслуживание библиотеки

### 7.1. Операции

- `review`: анализ содержимого библиотеки, выявление дублей, противоречий, отсутствующих зависимостей и устареваний;
- `create`: новый пакет навыка;
- `patch/refine`: точечная корректировка инструкций и файлов пакета;
- `merge`: объединение двух или более навыков с сохранением ссылок на происхождение;
- `split`: разбиение слишком широкого навыка на логические части;
- `archive`: исключение навыка из активного каталога без потери файла/истории;
- `restore`: восстановление из архива;
- `pin/unpin`: запрет автоматического архивирования и поглощения;
- `lock/unlock`: запрет любых автоматических изменений содержимого и состояния;
- `adopt/unadopt`: настройка политики автоматического обслуживания;
- `rollback`: восстановление выбранной версии;
- `export/import`: перенос пакета с валидацией.

**Никакое объединение не должно терять содержимое** `scripts/`, `references/`, `templates/`, `assets/`, относительные ссылки и необходимые зависимые файлы. При наличии потребителей старого `skill_id` создавать отображение `superseded -> target`, а при необходимости обновлять ссылки только после анализа зависимостей.

### 7.2. Состояния и политика

- `active → stale → archived`: по настраиваемым срокам и проверкам; стартовые значения можно предложить `30/90 дней`, но они не фиксированы.
- `archived → active`: по явному восстановлению.
- `active → superseded`: только после успешного применения merge.
- `pinned`: исключён из auto-архивирования/auto-merge.
- `locked`: запрещены изменения со стороны автоматических процедур; только явно авторизованное ручное действие владельца/администратора может снять блокировку.
- `manual` и `readonly`: автоматическая модификация и архивирование запрещены до явного `adopt`/разрешения.
- `use_count = 0` **не является** достаточным основанием для удаления/архивирования.

LLM-ревизия необязательна и настраивается отдельно от дешёвой детерминированной проверки. Никакого автоматического безвозвратного удаления; очистка архивов — отдельная подтверждаемая операция с резервной копией и аудитом.

### 7.3. Proposal-first workflow

Любая LLM-операция возвращает **proposal**, а не сразу изменяет файл:

1. Собрать целевые скилы, полные пакеты, связанные зависимости, provenance.
2. Построить план `create | update | merge | split | archive | restore`.
3. Создать новый пакет/patch в изолированной staging-области, указать diff, причины, затронутые файлы и источники.
4. Запустить проверки: схема SKILL.md, пути, хэши, секреты, ссылки, конфликт версий, политика владельца, потенциально опасные команды, размер, целостность зависимостей.
5. Если доступны тесты/контрольные сценарии скила — запустить безопасные проверки в изолированной среде; не исполнять произвольный код скила только для «проверки».
6. Применить после одобрения либо при явно настроенной auto-policy для разрешённых скилов и допустимого риска.
7. Атомарно записать файлы и метаданные, сохранить версию, вызвать reload, проверить каталог, завершить или откатить транзакцию.

Конфликт параллельного редактирования (`revision`/`package_hash` изменился) блокирует автоматический apply: proposal необходимо пересоздать или согласовать вручную.

## 8. Выполнение внутренних LLM-задач: **выбираемый режим**

### 8.1. Режимы

| Режим | Исполнение | VALERIA обязательна | Применение |
|---|---|---|---|
| `direct` | `ctx.experimental.generate.text()` или совместимая генерация без агентной сессии | Нет | анализ, классификация, предложения JSON |
| `session` | отдельная служебная сессия OpenCode (`ctx.session.create/prompt/wait`) | Нет | сложная агентная ревизия с инструментами |
| `valeria` | исполнение задания внутри VALERIA через внешний worker bridge/очередь VALERIA | Да, только для этого режима | централизованное управление ресурсами |
| `external` | внешний подключаемый исполнитель через тот же контракт worker | Нет | отдельный вычислительный сервис или оркестратор |
| `auto` | выбор из разрешённых режимов по политике доступности и возможностям | Нет | удобный режим по умолчанию |

`direct` по определению не может выполнять инструменты. Операции, которым требуются чтение/редактирование файлов, должны получать данные через серверное ядро и возвращать декларативный proposal либо переключаться в заранее разрешённый `session`/внешний режим. **Запись в каталог выполняет ядро**, а не произвольная команда LLM.

Ни один режим не является привилегированным по умолчанию; включение `valeria` не запрещает `direct` или `session`.

### 8.2. Приоритет настройки

1. Явный `execution.mode` в запросе конкретного задания.
2. Настройки для типа операции (`learning`, `review`, `merge`, `update`).
3. Настройки workspace/tenant.
4. Глобальная настройка плагина.

Для `auto` задаётся упорядоченный `preferred_modes` (например, `direct,session,external`), допустимые возможности и политика fallback. Fallback допускается только **до подтверждённого принятия** задания исполнителем; при неопределённом результате нельзя автоматически создавать ещё один LLM-run.

### 8.3. Параметры каждого задания

`model`, `provider`, `variant`, `temperature`, `max_tokens`, `max_iterations`, `timeout_sec`, `priority`, `max_cost_usd`, `max_parallel`, `execution.mode`, `fallback_policy`, `approval_mode`, `idempotency_key`, `scope`, `requested_by`.

Обязательны отдельные лимиты конкурентности по `executor`, `tenant/workspace` и глобально. Внешняя очередь VALERIA **не влияет** на лимиты других режимов; они управляются самим плагином. Возможность принудительного остановa, graceful pause, восстановления и наблюдения расходов.

### 8.4. Состояния задания

`created → queued → claimed/running → completed | failed | cancelled`; дополнительно `waiting_executor`, `retry_scheduled`, `waiting_approval`, `interrupted`, `unknown_outcome`.

`Job` хранит `job_id`, `operation`, `scope`, `executor_mode`, `status`, `attempt`, `created_at`, `updated_at`, `progress`, `cost`, `source_refs`, `proposal_ids`, `error`, `lease`, `correlation_id`.

Повтор после потери соединения не должен порождать второго исполнителя: `idempotency_key`, durable lease с TTL, heartbeat, сверка факта завершения и политика `unknown_outcome`.

### 8.5. Интеграция с очередью VALERIA — необязательный адаптер

Для режима `valeria` реализовать pull-worker:

1. Плагин создаёт `Job` со статусом `waiting_executor`/`queued` и режимом `valeria`.
2. Авторизованный bridge VALERIA периодически вызывает `jobs.lease` с типом `valeria`; получает атомарно закреплённое за ним задание и его входные данные.
3. VALERIA создаёт свою обычную задачу/сессию, сохраняя `job_id`, `idempotency_key`, `correlation_id`; может выполнить её через собственную FIFO-очередь.
4. Bridge посылает `jobs.heartbeat` и прогресс; по завершении — `jobs.complete` с структурированным LLM-результатом либо `jobs.fail`.
5. Плагин валидирует ответ, создаёт proposal и далее применяет свою policy. VALERIA **не пишет** файлы скилов в обход ядра.
6. При timeout/рестарте bridge сверяет уже принятые и выполненные VALERIA задачи по durable marker; не создаёт дубль при неизвестном исходе.

Такой же интерфейс использует режим `external` с другим `worker_kind`. Запуск задания из VALERIA через RPC с `execution.mode=direct` или `session` всегда остаётся допустимым — это **не** означает передачу в очередь VALERIA.

## 9. Менеджер скилов: интерфейс OpenCode

Команда `/skills-manager` открывает собственный TUI route в OpenCode v2. Быстрые команды: `/skills-review`, `/skills-learn`, `/skills-jobs`, `/skills-settings` (точные имена допускают настройку алиасов).

Экран менеджера содержит:

- таблицу с поиском, фильтрами (`scope`, `owner`, `managed`, `state`, `tag`, `used`, `changed`) и сортировкой;
- панель выбранного скила: описание, содержимое всех файлов, provenance, версия, использование, зависимости;
- мультивыбор для `merge`, `archive`, `pin`, `adopt`, `export`;
- список предложений с diff до/после и индивидуальным `approve/reject`;
- кнопки `Review all`, `Learn history`, `Sync catalog`, `Undo/Rollback`;
- журнал задач: исполнитель, статус, прогресс, попытки, затраты, ошибка, кнопки cancel/retry;
- настройки запусков (в том числе отдельные режимы LLM-исполнения), бюджетов и политик автообслуживания;
- журнал аудита и просмотр архива;
- подтверждение потенциально разрушительных действий и предупреждение при изменении ручных скилов.

Использовать поддерживаемые TUI возможности: команды/keymap, JSX routes, dialogs, подписки на RPC-события. Не привязывать серверную логику к наличию открытого TUI. При использовании VALERIA интерфейс менеджера строится в её веб-приложении поверх **того же RPC API**; серверный RPC не может гарантированно «открыть окно» в произвольном локальном TUI-клиенте, поэтому `manager.open` — локальная TUI-команда, а `manager.snapshot` — публичная API-операция.

## 10. Публичный API для VALERIA (обязателен)

### 10.1. Транспорт

Типизированный RPC v1 на базе `Rpc.define` с экспортом контракта `opencode-skill-curator/rpc`; сервер регистрирует реализацию через `ctx.rpc.register`. Внешние клиенты вызывают RPC через `@opencode/client` и сервер OpenCode. Отдельный REST-сервер не требуется. Если VALERIA нужен Python/HTTP без TS-клиента, предоставить документированный HTTP-compatible bridge/SDK с теми же схемами, идентичными правами и ошибками (не выдумывать нестабильные OpenCode HTTP-маршруты).

Все методы используют `scope={tenant_id?,workspace_id?,directory?}` и контекст аутентифицированного вызывающего субъекта; scope **определяется серверной авторизацией**, а не только присланными строками. API должен работать как локально, так и при удалённом размещении VALERIA при наличии безопасного сетевого доступа к OpenCode.

- `skill.created`, `skill.updated`, `skill.archived`, `skill.restored`, `skill.merged`, `skill.locked`;

- `job.created`, `job.started`, `job.progress`, `job.waiting_executor`, `job.completed`, `job.failed`, `job.cancelled`;
- `settings.changed`, `manager.refreshed`, `health.changed`.

Payload: `event_id`, `occurred_at`, `scope`, `actor`, `correlation_id`, `entity_id`, `entity_revision` и типизированные детали. События доступны подписчикам, **но при разрыве подключения пропущенные события восстанавливаются через `events.replay`**. Идемпотентность обработки событий на стороне VALERIA.

### 10.4. Примеры логических запросов

Запуск ревизии *не через очередь VALERIA*:

```json
{
  "method": "curator.review",
  "input": {
    "scope": {"workspace_id": "ws-12"},
    "skill_ids": ["gitlab-auth", "gitlab-token-fix"],
    "execution": {"mode": "session", "max_cost_usd": 0.75},
    "dry_run": true,
    "idempotency_key": "review-ws12-20261113"
  }
}
```

Запуск через очередь VALERIA:

```json
{
  "method": "learning.run",
  "input": {
    "scope": {"workspace_id": "ws-12"},
    "session_ids": ["ses-001", "ses-002"],
    "execution": {"mode": "valeria", "priority": "low"},
    "idempotency_key": "learn-001-002"
  }
}
```

Управление вручную:

```json
{
  "method": "skills.archive",
  "input": {
    "scope": {"workspace_id": "ws-12"},
    "skill_id": "obsolete-deploy",
    "expected_revision": 7,
    "reason": "Заменён на deploy-v2",
    "idempotency_key": "archive-obsolete-deploy-r7"
  }
}
```

Это **логические RPC-конверты контракта**, а не обещание существования маршрута вида `/api/curator/review`: реальная передача выполняется клиентом OpenCode RPC или совместимым адаптером.

### 10.5. Стандарты ответа и ошибок

Управляющий запрос возвращает: `request_id`, `correlation_id`, `resource_id`/`job_id`/`proposal_id`, `status`, `revision` (если применимо), `created_at`. Тяжёлые операции всегда асинхронны: ответ — приём задания, а не готовый diff.

Типизированные ошибки: `unauthorized`, `forbidden`, `not_found`, `validation_error`, `revision_conflict`, `scope_violation`, `locked_skill`, `readonly_skill`, `executor_unavailable`, `rate_limited`, `budget_exceeded`, `idempotency_conflict`, `lease_expired`, `unknown_outcome`, `internal_error`. Не раскрывать приватные пути и секреты в ошибках другим арендаторам.

## 12. Безопасность и многопользовательская работа

1. **Разделение арендаторов:** сессии, навыки, токены, архивы, proposals и задания одного tenant/workspace недоступны другому по умолчанию. Глобальные навыки публикуются только после явного разрешения администратора.
2. **Авторизация API:** сетевой доступ к OpenCode защищён его механизмом аутентификации; поверх него плагин проверяет права приложения и разрешённый scope. Права `viewer`, `editor`, `curator`, `administrator`, `worker`. Не доверять клиентскому `tenant_id` без серверной привязки.
3. **Права на файлы:** allowlist корневых директорий; проверка realpath; защита от `..`, symlink traversal, hardlinks вне разрешённой области. Внешние пакеты readonly по умолчанию.
4. **Недоверенная история:** тексты пользователя, вывод инструментов и найденные документы являются **данными**, а не инструкциями для куратора. Использовать строгие системные правила, типизированный вывод, проверку предложений и запрет прямых shell-команд при применении.
5. **Секреты:** фильтрация API-ключей, cookie, паролей, токенов, приватных путей и PII до отправки модели и до записи в SKILL.md; маскирование в логах и отчётах.
6. **Внешние исполнители:** worker получает минимально необходимый контекст, отдельно конфигурируемый уровень раскрытия, подписанный/аутентифицированный канал, lease-bound capability; worker не может самовольно сделать `proposals.apply` без прав.
7. **Approval:** пользовательские и сторонние скилы не изменяются автоматически. `pin` и `lock` должны соблюдаться всеми путями публикации; административный override только явным действием с reason/audit, не инструкцией модели.
8. **Политика исполнения кода:** скилы могут содержать скрипты, но их нельзя автоматически выполнять без изоляции и установленной политики. Просмотр содержимого не равен запуску.
9. **Версии:** любое изменение имеет автора, источник, diff, контрольную сумму и способ отката; не журналировать полные секретные транскрипты.
10. **Отказобезопасность:** при повреждении БД, утрате разрешений, неопределённом результате внешнего задания или ошибке валидации — блокировать публикацию и показывать причину.

## 13. План разработки

### Этап A — ядро и API

Подключение к OpenCode v2, каталог скилов, локальная БД, стабильные `skill_id`/revision, создание/редактирование/архив/restore, versioning, RPC, аутентификация и audit; TUI список и просмотр. **Результат:** VALERIA может программно управлять библиотекой без LLM.

### Этап B — исполнитель и jobs

Машина состояний, `direct`/`session`, настройка режимов, лимиты, budget, отмена, retries, идемпотентность; bridge `valeria` и `external` с durable lease. **Результат:** один job можно запустить в любом разрешённом режиме, независимо от очереди VALERIA.

### Этап C — Learner

Сбор событий, ретроспективный импорт, защита от рекурсии, извлечение кандидатов, поиск существующих скилов, генерация proposals. **Результат:** завершённые рабочие задачи дают проверяемые предложения на новые навыки и улучшения.

### Этап D — Curator

Дубликаты, merge/split, package-aware preservation, stale/archive, тесты/валидация, approvals, rollback, TUI diff и пакетные операции. **Результат:** библиотека поддерживается актуальной автоматически и вручную.

### Этап E — интеграция VALERIA и полировка

Панель администратора VALERIA через RPC, monitoring/events, привязка tenant/workspace, метрики, стресс-тесты восстановления, документация и npm-публикация.

## 14. Приёмочные критерии (Definition of Done)

1. Плагин запускается в чистом OpenCode v2 **без VALERIA**; можно открыть `/skills-manager` и управлять скилами.
2. Из VALERIA через RPC можно получить весь разрешённый каталог, содержимое, версии, список предложений, состояние jobs и настройки.
3. Из VALERIA можно создать/обновить/объединить/архивировать/восстановить скил с безопасной проверкой прав и версий.
4. `curator.review` и `learning.run` принимают `execution.mode=direct`, `session`, `valeria`, `external`, `auto`; каждый работает при настроенном исполнителе.
5. Если пользователь выбрал `direct` или `session`, задания **не отправляются** в очередь VALERIA; если выбрал `valeria`, они исполняются в ней.
6. Режим запуска выбирается на уровне вызова, операции и настроек. Изменение настройки не переносит активное задание.
7. Если VALERIA отключена, независимые режимы продолжают работать; для явно выбранного `valeria` возвращается `executor_unavailable`, если нет bridge.
8. Прерванная связь с VALERIA не создаёт дублирующие LLM-задачи; неизвестный исход помечается и согласуется.
9. Две одновременно одобряемые модификации одного навыка не затирают друг друга: одна получает `revision_conflict`.
10. Повторный RPC-запрос с тем же idempotency key не создаёт дубль операции; конфликтующий payload отклоняется.
11. Автосистема не меняет `manual`, `readonly`, `locked` и `pinned` навыки вопреки policy; ручное снятие блокировки логируется.
12. Объединение сохраняет все необходимые файлы, пути, зависимости и обоснования; исходные пакеты доступны для восстановления.
13. После перезапуска сохраняются навыки, версии, proposals, настройки, leases и jobs; выполнение корректно восстанавливается.
14. Ошибочный/вредоносный текст в диалоге не может сам активировать применение proposal, изменить настройки или получить доступ к чужому workspace.
15. Секреты из транскриптов не попадают в опубликованные SKILL.md и внешние исполнительские payloads при запрещённой передаче.
16. Трассировка каждого изменения: источник → learning candidate → proposal → approval → версия → audit.
17. `dry_run` показывает потенциальные изменения без записи в файлы.
18. Вызов `ctx.skill.reload()` или эквивалента обеспечивает появление новых навыков в последующих сессиях без ручного рестарта, если это поддерживается установленной версией OpenCode.
19. Документация включает установку, конфигурацию, примеры RPC, интеграцию с VALERIA, политику безопасности, upgrade и troubleshooting.
20. CI покрывает unit, integration, permission tests, contract tests для RPC, crash/retry tests и end-to-end сценарии создания/слияния/отката.

## 15. Необходимые тестовые сценарии

- Новая сессия дала успешное решение → LearningCandidate → предложение нового SKILL.md → одобрение → доступность в OpenCode.
- Три похожих навыка → merge proposal → diff → apply → старые пакеты архивированы, новый доступен.
- Частично совпадающие навыки → Curator отказывается от небезопасного слияния и объясняет причину.
- Скил не использовался 90 дней, но locked/pinned/manual → не архивируется.
- Валидатор обнаружил опасный путь/утечку токена → публикация заблокирована.
- Ручное изменение скила после генерации proposal → `revision_conflict`, без перезаписи.
- Долгая пользовательская сессия и параллельная ревизия → независимая работа, отсутствие взаимной блокировки.
- Режим `direct` → без OpenCode-agent session и без VALERIA queue.
- Режим `session` → отдельная служебная сессия исключена из самообучения.
- Режим `valeria` → lease/heartbeat/complete, повторный запрос с прежним idempotency key возвращает тот же job.
- Bridge VALERIA умер после создания задачи → восстановление по durable marker, отсутствие дубля.
- Режим `auto` при отключённой VALERIA использует разрешённый локальный executor.
- Многопользовательский тест: другой tenant не может читать приватный скил и diff даже зная их ID.
- Перезапуск OpenCode во время apply → либо полностью применённая валидная версия, либо откат, без полуразрушенного пакета.

## 17. Техническая привязка к актуальному OpenCode v2

Подтверждённые примитивы официального SDK, на которые можно опираться при реализации:

- `Plugin.define`, части `server`, `tui`, `rpc`;
- `ctx.rpc.register` / `Rpc.define`, внешний вызов через `@opencode/client`;
- `ctx.skill.list`, `ctx.skill.transform`, `ctx.skill.reload`;
- `ctx.session.create`, `ctx.session.context`, `ctx.session.prompt`, `ctx.session.wait`, `ctx.session.list`;
- `ctx.experimental.generate.text` (**экспериментальный API**, нужен адаптер совместимости);
- `ctx.event.subscribe`, `ctx.tool.hook('execute.before'/'execute.after')`;
- `ctx.storage.get/set/scan`;
- TUI `context.ui.router.register`, `context.keymap.layer`, диалоги;
- подписки на RPC-события.

**Важно:** имена RPC-методов в разделе 10 и конфигурация в разделе 11 — **требования к новому плагину, а не уже существующие методы OpenCode**. Структура транскрипта, точные lifecycle events и полнота истории должны быть подтверждены на закреплённой версии SDK интеграционными тестами; если часть данных недоступна штатным `session.context`, предусмотреть event capture/источник импорта, а не предполагать магический доступ к архиву.
